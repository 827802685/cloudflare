# 06 · 架构方案与技术选型

## 1. 从实测结果直接推出的三条硬约束

1. **必须有自建网关。** `api.cloudflare.com` 不发 CORS 头，预检 `OPTIONS` 直接 400。浏览器和 Capacitor WebView 都逃不掉 —— 所以"App 直连官方 API"这个选项在技术上不存在，除非用原生 HTTP 客户端（见方案 C）。
2. **网关必须绑你自己的域名。** `*.workers.dev` 在本机不可达（超时 + DNS 被解析到 `108.160.166.148`）。`acct.example.com` 实测可达、能正常返回 Worker JSON，所以网关就绑在你已有的这个 apex 或其子域上（**新增域名绑定是写操作，等你授权**）。
3. **令牌判断不能用 `tokens/verify`。** 你这把是 account-scoped，`/user/tokens/verify` 恒返回 `401 code 1000`。登录态一律用 `GET /accounts` 成功与否判断。

## 2. 三条路线的取舍

| | A · PWA + 自建 Worker 网关（推荐） | B · A + Capacitor 出 APK | C · Flutter 原生 App |
|---|---|---|---|
| 形态 | 手机浏览器/加主屏 | WebView 壳 + 同一套 Web 代码 | 真原生 |
| API 调用 | 必须走网关（同 A） | 同 A | **可直连** `api.cloudflare.com`（原生 HTTP 无 CORS），网关只是用来藏令牌 |
| 本机能否出包 | 不需要出包，部署即可用 | ❌ 本机无 Android SDK/Gradle，只有 JDK 8 → 必须靠 GitHub Actions | ❌ 本机无 Flutter SDK，且要装 Android SDK + NDK，最重 |
| 首版见效速度 | 最快（今天就能在手机上用） | 中等 | 最慢 |
| 维护成本 | 一套代码 | 一套代码 + 一个壳 | 与 Web 完全分叉 |
| 风险 | 浏览器缓存/Service Worker 更新不及时会让"版本列表看着是旧的"，要在 UI 上做显式刷新 | APK 依赖 Actions artifact 下载（要登录，国内不稳） | 全量重写 |
| 对 `workers.dev` 不可达的抗性 | 靠自定义域名（已验证可行） | 同 A | 同 A，但直连 API 时不需要域名前置 |

**推荐：A 先跑起来，B 作为 A 的壳顺带产出（同一套代码，加壳不改逻辑），C 不选。**

`cloudflare-mobile`（下面 §5）之所以选 Flutter，是因为它想彻底绕开 CORS 和网关；代价是要自己实现全部 UI、并且没有 Web 版。你现在的需求（自己用、要快、还要能在电脑浏览器上一起看）不适合这条路。

**2026-10-10 用第三个项目验证了这张表的"API 调用"那一行**：读 `CloudFlareAssistant` 源码（Kotlin 原生，即方案 C 的同类），它的 Retrofit base 写死 `https://api.cloudflare.com/client/v4/`，全仓没有任何后端/代理工程（`08` §7.1）—— 所以"原生 App 不需要网关"不是推测，是这类项目的实际做法。但它把 CF 令牌当 Room 实体的明文字段存在手机里（`AuthHelper.kt:20-26`，`08` §7.2），这正是我们坚持走网关的理由：**C 路线省掉一个 Worker，代价是账号级凭据落在手机上**。结论不变，仍选 A（B 顺带）。

## 3. 底座选择：**自研为主，MIT 项目作参考**

- **不能 fork** `a422015028/CloudFlareAssistant`（你 star 的那个）：源码公开可读，但**根目录只有 `README.md` / `README_CN.md` / `RELEASE_NOTES_v7.8.5.md`，没有 LICENSE 文件**，GitHub API 的 `license` 字段为 `null`，`/repos/.../license` 端点 404。README 自称 MIT 但没有许可证正文 → 法律上默认"保留所有权利"，只能把它的功能/端点清单当参考资料，不能拿来改。它的构建配置还写死了作者本机 `«LOCAL_PATH»`，也说明它不是一个能直接接手的工程。
- **可以合法借鉴** `hefy2027/cf-manager`（MIT ✅）：Vue3 + Naive UI + Pinia + Express 后端 + Hono Worker，覆盖面与我们目标最接近（多账号、配额、Workers/Pages 部署、DNS、KV/D1/R2、规则引擎），凭据还做了 AES 加密存储。**借鉴方式是"读它的 API 调用组织形式"，不是复制代码**。对外措辞要按"参考 MIT 开源项目 + 自己实现"写，不说成全部自研。
- **可以合法 fork** `hasanzadee/cloudflare-mobile`（Apache-2.0 ✅，有签名 APK）：如果哪天想走 C 路线，这是起点；现在不做。

  .github\workflows\     # 只有走 B 路线时才需要

### 4.1 为什么 API 层要自己写而不用官方 `cloudflare` npm SDK

本次实测把原因坐实了：官方 SDK 假设的是**统一信封**，而真实响应里我们至少遇到四种拆包方式 ——

| 来源 | 结构 |
|---|---|
| 普通 REST 列表 | `result: [...]` + `result_info` |
| Workers 版本 | `result: {items: [...]}` + `result_info` |
| Workers 部署 | `result: {deployments: [...]}` |
| Analytics SQL | 顶层 `{data, rows, statistics}`（**没有 success 字段**） |
| GraphQL | `{data, errors}`，HTTP 恒 200 |
| 代码下载 | `multipart/form-data` 文本（不是 JSON） |
| DNS 导出 | 纯文本 zone 文件 |

所以要自己写：`createCfClient({auth, baseUrl}).request(path, {unwrap: "result|items|deployments|data|text|multipart"})`，统一处理 429/5xx 退避（CF 全局限流约 1200 请求/5 分钟/IP）、分页（`result_info.total_count`，**不是** `X-Total-Count`）、以及 §2 of doc 02 说的"后缀回落"陷阱（校验 `content-type`）。域模块按 `zones / dns / workers / pages / kv / d1 / analytics / domains` 分，每个都很薄。

### 4.2 网关必须是**白名单路由**，不是透明转发

透明 `/api/* → api.cloudflare.com/*` 等于把一个持有你令牌能力的开放代理放在线上：会被别人烧令牌，还有 SSRF 风险。设计上：

- 只注册我们 App 真用到的路径（用 `01`–`04` 分册那张端点表当唯一来源，一条一条写死 + 参数校验）；
- 设备侧首次启动生成 `deviceId` + 随机 secret，服务端 KV 白名单（或 HMAC）校验；
- CF 真令牌只存在于 `wrangler secret put CF_API_TOKEN`；
- 设置页保留三种模式：**网关（默认）/ 直连 `api.cloudflare.com`（仅原生或本地调试用）/ 自定义 Base URL**（将来给域名前置留口子）。

免费 Worker CPU 只有 10 ms/请求，所以网关**只做转发、鉴权、改写头**，绝不解析那个 2.5 MB 的代码 multipart —— 代码下载让手机端直连（原生）或者干脆降级为"不含代码预览"。

### 4.3 本地开发怎么绕 CORS

`vite server.proxy` → `wrangler dev`（本地 8787）。这条链路已在 `«LOCAL_PATH»` 沙箱里验证过：本地 Worker 出站访问 CF API 成功拿到真实账号数据。所以**整个开发闭环在部署之前就能全程验证**，只有生产 CORS、真实上传尺寸、wss tail、presign 这四类必须上线后才能确认。

## 5. 按四块功能排出的界面结构（3 条主导航就够）

移动端菜单我按你的"最小侵入面"习惯压到三条：

1. **流量** — 大数字（1d 汇总）+ 国家 Top（adaptive）+ 状态码环 + 按主机名下钻（SQL）；每台 Worker 的流量用"域名 → service"映射归属（`01` §5）。
2. **Workers** — 脚本列表（7 个）→ 版本列表（分页 + `total_count=148`）→ 版本详情（`resources` 对比）→ **切换/灰度**（`versions[]` + 强制填 `workers/message`）→ 密钥名 / cron / 自定义域名。Pages 卡片先做成"当前账号无项目"的空状态。
3. **域名** — Workers 直挂域名（6 条）/ Zone 路由（1 条）/ DNS 记录（14 条）三个分区 + 站点设置（56 项，44 可编辑）+ 清缓存。

Pages 的版本与切换在拿到真实项目前只做只读占位；这一点在 `09` 里列为未验证项，不算完成。

## 6. 现在能定 / 还不能定

已经定死（有实测支撑）：网关必要性、网关域名策略、API 拆包策略、数据源选择（SQL + GraphQL 双路）、令牌判断接口、错误码分支、Workers 版本/部署的全部读路径、自定义域名读写语义。
