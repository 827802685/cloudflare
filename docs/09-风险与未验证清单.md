> **B 这一节的"已确定"在 10-10 深夜之前全都是鉴权层的确定，不是写成功的确定。** 口径现在要更新一次：**确实发生过成功的写调用了** —— `wrangler deploy`（两次）、`wrangler secret put`（三个 + 深夜第二段换令牌那次共四个）、`PUT workers/domains`（一次，就是 B3）、`POST accounts/{a}/tokens`（一次，新建控制台令牌，见 `05` §1.5）。它们证明的是"这把令牌能写、CF 收我们的请求"，**不等于 App 的业务写链路可用**：版本切换 / 回滚 / 灰度 / DNS 增删改 / 清缓存 / Pages 部署**仍然一条没实测过**（B1、B2、B4–B6 原样有效），网关对它们也仍然一律 501。任何"某条写路由能用了"的说法都得等 4.4 在测试 Worker 上真跑一次才算。
> 唯一的例外是 B5 那条 purge 探测：它不是"被拦住"也不是"业务校验拒绝"，而是**真的执行了**（等效空操作）。写链路的危险程度在这种地方看得最清楚 —— 不能拿"我们以为会被拒"当依据。
>
> 2026-10-10 晚间我把这条界线搞混过一次：`05` §3 那张**手抄**权限表写着绑域名要 `DNS Write`，我没回 `10` 的**生成表**核对就排了个"4.3 必须先于 4.2"的顺序，结果生成表里那一条只有 `Workers Scripts Write`，而深夜那次真请求又证明 CF 建那条记录时压根不查令牌的 DNS 权限。教训两条：① 手抄表和脚本生成表冲突时以生成表为准，并且要顺手把抄错的那行改掉（已改）；② 排期结论（"必须先做 X"）比事实陈述更容易伤人，因为它会改变别人的动作顺序，下这种结论前必须回到权威来源复核一次，而不是引用自己的二手笔记。

## E. 客户端实现层的坑（已经踩到，别再踩）

1. **Workers 路由会忽略未知路径后缀并回落成父资源** → `versions/{v}/content` 返回的是版本 JSON，`scripts/{s}/analytics` 返回的是整包代码。**只看 HTTP 200 会写出"下载成功但界面显示一坨 JSON"的 bug**，必须校验 `content-type` + 关键字段。
2. **Workers 脚本名在 `id` 字段，不在 `name`** → 用 `name` 会一路 404 `10007 This Worker does not exist`。
3. **列表信封不统一**：`result:[]` / `result:{items}` / `result:{deployments}` / 顶层 `data` / GraphQL `data` / multipart 文本 / DNS 导出的纯文本 zone 文件。封装层要按路由指定拆包策略。
4. **分页在 `result_info.total_count`**，不是响应头。
5. `tokens/verify` 对 account-scoped 令牌恒 401 `code 1000` → 登录态判断改用 `GET /accounts`。
6. `405 code 10405 Method not allowed for this authentication scheme` 是**动词不对**（如 `GET /workers/tails`），不是权限问题。
7. **没有"下载指定历史版本源码"的公开接口** → 只能下载当前部署整包（实测 2 558 574 字节）。"版本代码对比"这个需求要做成"当前版本 vs 我本地缓存的上一次"，不能承诺任意两版本 diff。
8. `PUT …/schedules` 是**整体替换**，改 cron 前必须先读全量。

17. **"取不到"和"真的是 0"在界面上必须长得不一样，而且这条会在三个时机踩**（2026-10-10 用浏览器实测抓到，同一个屏上同时错了两处）：
    - **失败时**：拿假设备令牌打网关，网关如实返回 `401 {"kind":"auth","message":"设备令牌不对"}`，但看板渲染成「请求数 0 / 状态码：这个时间窗内确实没有数据」。用户读到的是"我的站点没人访问"，真实情况是"根本没连上"。
    - **加载中时**（原先没意识到这也算错）：首次进入的那 1–4 秒 `ov` 还是 null，同一组卡片显示「请求数 0」，而"出口流量"因为 `bytes(0)` 本来就渲染成"—"，于是同一屏出现"0"和"—"并存的自相矛盾。**只要有任何一个指标把 0 渲染成占位符，其余的 0 就一起变成谎言**。
    - **超时被说成"连不上"**（同日抓到的第四处）：连点两次"查询"把本地网关压到 25 秒不返回，界面报的是 `Failed to fetch · network` + 「连不上网关，检查地址是否可达、手机和电脑是否同一网络」，而真实情况是 **TCP 早就通了**。已在 `app/console/src/lib/api.ts` 拆出独立 `kind: "timeout"`（只给 `AbortSignal.timeout` 抛的 `TimeoutError`），文案明说"能等到超时说明连得上，别去查网络，先看 CF 上游慢不慢、这一档扫描行数大不大"；`network` 只留给 fetch 立刻 reject 的情形，设置页那条 8 秒的 `/health` 探测也走同一分类。**验证方法记下来**：本机起一个"接受连接但永不 `res.end`"的小服务（连 CORS 预检 `OPTIONS` 一起挂住，实测日志里就是 `held: OPTIONS /v1/overview?range=7d`），把预览 origin 的网关地址指过去，25 秒后界面如实显示「网关 25 秒没响应 · timeout」；先用 40 秒自杀版试过一轮，那一轮服务先退出、socket 被关，界面报 `Failed to fetch · network`——**那一次不是 bug，而是"连不上"分支的正确行为**，两种情形刚好都验到了。
    已修（`app/console/src/views/BoardView.vue`）：`blank = !ov` 统一走占位符"—"，文案按 `dead = err && !ov` 分两档 —— 失败是「没取到，不是 0」、路上是「取数中…」；`blank` 时不画时序图；空态分「没取到 / 取数中」与「这个时间窗内确实没有数据」，后者只在**数据确实回来了且为空**时出现（Pages 项目 0 个就是这种合法空态，界面上另有 `404 8000007` 那条实测注记支撑）。下钻卡片同样拆成「还没查 / 查询中… / 查询完成了，这一档确实没返回条目」，不再让口径说明冒充空态。四档都在浏览器里实测过：假令牌 → auth、挂起服务 → timeout、`fetch` 打桩 → 取数中、真令牌 → 21,529 请求与下钻 `blog.acct.example.com 5477` 等真实数字。
    **教训**：`x ?? 0`、`x || 0` 这类"把缺失折叠成 0"的写法，在会遭遇采样/套餐拒绝/网络失败的 API 前端里等于随机撒谎；`reduce` 求和对空数组天然给 0，所以**聚合指标比单字段更容易中招**。自检时不要只看错误分支，**加载中的第一帧也要看**（这次就是靠第一帧抓到的）。同样的道理适用于错误分类：**把"慢"和"连不上"合并成一个 `network`，等于让用户去查本来没坏的网络**。

18. **Node 24 + Windows 上不要用 `process.exit()` 收尾自检脚本**（2026-10-10 晚间踩到）：全绿的一轮 `check-pwa-assets.mjs` 反而返回**退出码 127**，并打出 `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), file src\win\async.c`。原因是脚本里 `fetch` 留下的 undici keep-alive socket 正在关闭，此时调用 `process.exit()` 会撞进 libuv 的 Windows 断言。已把 `smoke-gateway.mjs` 和 `check-pwa-assets.mjs` 统一改成设 `process.exitCode` 后自然退出，实测三种结果都对得上（全绿 0 / 有不合格引用 1 / 基址没起服务 2）。**教训**：CI 里"检查器返回 127"会被读成"检查器崩了"，而这次崩的是退出方式、不是检查内容 —— 判断脚本状态要同时看它最后一行输出，别只看退出码。同类地，`check-pwa-assets.mjs` 以前在基址没起服务时输出一整屏 `ERR` 行，得从下往上翻才知道"哦，服务没开"，现在开头就一句人话再退 2。

19. **界面上还有第四类"没有数字"：已失效的用户选择**（2026-10-10 晚间，多账号读侧做完后**自己造状态**才看见的，与 `E17` 同族）：`?account=` 校验做完之后，localStorage 里完全可能存着一个**已经不在可见集合里**的账号 id（后台改了令牌作用域，或者你上次选的是别的账号）。这时界面上错了两处：
    - 那一行还标着「**当前**」—— 它不是当前，是遗留的失效值，别的屏正在为它 422。
    - **同一张卡片里两句话互相矛盾**：上面一行说"这个账号已经不可见了"，下面正文还写着"界面上所有数据都来自它"。

    **教训**：三态文案（没取到 / 取数中 / 确实没有）覆盖不了"存着一个不再成立的选项"这类状态，它是第四类，得单独有一句。验证方法也记下来：**主动构造失效状态**（手改 localStorage 里的 id）比只测正常路径多抓得出这类错；而"两句各自都对的话拼在同一张卡片上"必须**整屏读一遍**才发现，读源码是看不出来的。

20. **wrangler 配置的两条 Windows/TOML 面坑（10-10 深夜部署时踩到）**：
    - **顶层键必须放在所有 `[表]` 之前**。我把 `workers_dev = false` 追加在 `[dev]` 段下面，它就被解析成 `[dev]` 的字段，wrangler 只给一句 `Unexpected fields found in dev field: "workers_dev"` 就**当没看见继续部署** —— 不报错、不生效，属于最难受的那类失败。现在 toml 里写了注释钉住这条。
    - **静态壳 + API 同域名要靠 `run_worker_first` 数组**。`[assets] not_found_handling = "single-page-application"` 会把**所有**未命中 assets 的路径回 index.html，`/v1/*` 一起被吞，界面上表现为"所有请求都 200，但返回的是一坨 HTML"（和 `E1` 是同一类坑：200 不等于对）。必须显式 `run_worker_first = ["/v1/*", "/health", "/api/*"]`。前端 `api.ts` 只看 content-type 才拦得住这种情形 —— 这条已在冒烟里（39 条打的是 JSON 字段断言，HTML 会当场失败）。
    - **`wrangler deploy` 在 Git Bash 里要先 source `.dev.vars`**：它读 `CF_API_TOKEN`/`CF_ACCOUNT_ID`（deprecated 但可用）或 `CLOUDFLARE_API_TOKEN`。忘了 source 时报的是"non-interactive 需要 CLOUDFLARE_API_TOKEN"，接着它会试图拉 `--temporary` 预览账号 —— **差点把东西部署到别人的临时账号上**，看到这句要停下来确认身份，不要顺手加 `--temporary`。
    - 顺带一条老坑复现：那次失败的 deploy 结尾又是 `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` + 退出码 127（`E18`），所以**判断 wrangler 成功与否要看它有没有打 "Uploaded/Deployed" 那两行，不能只看退出码**。

21. **建 API Token 时 `resources` 只认嵌套写法（10-10 深夜实测）**：给 zone 级权限组建令牌，`resources: {"com.cloudflare.api.account.zone.*": "*"}` 被拒 —— `400 code 1001 "Must specify a zone for account owned tokens, or nest zone under specific account resource"`；要写成 `{"com.cloudflare.api.account.<ACC>": {"com.cloudflare.api.account.zone.*": "*"}}`。**和读回来的形状一致**：`GET /accounts/{a}/tokens` 里那条 zone 策略本来就是这种嵌套形态，所以"照抄 GET 的形状去 POST"是对的，反过来（拿文档里平铺的 zone id 例子）会撞。

22. **"故意非法的写探测"不能对 purge 这类端点用（`B5` 那条踩的就是这个）**：我们原先的探测范式是"填一个明显非法的 payload，看错误停在权限层还是业务层"，这个范式对 `dns_records` 有效（缺字段 → `9000 DNS name is invalid`），但 `purge_cache` 对 `files:[123]` **直接回 200 并执行**。范式失效的地方不是 CF 变了，是**每个端点对"非法"的容忍度不一样**。下次要区分权限，改用「不存在的 zone id」这类**必然 404 又不可能有副作用**的坐标，而不是赌它会把 payload 拒掉。

23. **本机 `wrangler dev` 起之前先数端口（`C7` 的可复现成因）**：Windows 允许同一个 `127.0.0.1:8788` 被多个进程重复 bind，第二次、第三次启动**不报"端口占用"，只是静默失效**，`Ready on http://127.0.0.1:8788` 照打，而请求会被派给半死的实例 —— 表现就是"连 `/health` 都挂十几秒"。起之前 `netstat -ano | grep ':8788' | grep LISTENING`，行数 >1 就先把旧的 node/workerd 全杀掉再启动。
