### 10-10 晚间这一轮（多账号读侧 + 界面又抓到两处说谎，仍然只读、零账号变更）

起因是你问了一句"支不支持多账号"。答案是**当时不支持**：所有 CF 路径都由 `catalog.ts` 里同一个 `ACC(env)` 生成，账号 id 只能来自网关 env（本地 `.dev.vars` / 线上 secret），换账号等于改配置重启。这一轮把**读侧**补齐了，写侧一条没碰。

6. **网关侧多账号读侧**（路由 **27 → 28** 条）：
   - 新增 `GET /v1/accounts`：返回令牌可见的账号全量列表，外加三个状态字段 —— `active`（这个请求实际用的账号 id）、`requested`（客户端带了 `?account=` 没有）、`applied`（那个 id 在不在返回列表里）。**三个字段而不是只给 `active`**，是因为界面要能区分"网关默认账号"和"你选的账号已经失效"，只有一个字段就必然要猜。
   - `?account=` 闸门：先按 `^[0-9a-f]{32}$` 判形状，再拿 `visibleAccountIds()` 的可见集合做白名单，落不进集合就 `422 badQuery`。顺序很重要 —— **闸门挂在设备令牌中间件之后**，不然没登录的人也能借这个参数触发 CF 调用。合法就 `c.set("acctEnv", {...c.env, CF_ACCOUNT_ID: want})`，业务路由统一改走 `E(c)` 取 env，第 1 条硬规则（客户端传不进任意账号）没被削弱：路径里的账号片段只能取自 `/accounts` 的返回集合。
   - `/v1/accounts` **豁免** `?account=` 校验。这条是被冒烟脚本抓出来的：第一版只在客户端做了豁免，网关照样 422，于是"存储里的账号 id 失效"变成死锁 —— 连账号列表都取不到，只能去清 localStorage。自救路径必须无条件可达。
   - `visibleAccountIds()` 结果按令牌缓存 5 分钟、只活在内存，避免每次带 `?account=` 的请求都多打一次 `/accounts`（`09` §C4 的限流面）。
   - `/v1/zones` 在网关侧按 `z.account.id` 本地过滤。刻意**不用** CF 那个 `?account_id=` 查询参数 —— 它没实测过；证据里 zone 对象本来就带 `account.id`，用已确认的字段够用。缺 `account.id` 的条目**保留**：不能因为接口少给一个字段就把它判成"不属于这个账号"。
7. **前端接线**：`config.ts` 的 `Config` 加 `account` / `accountName`（storage key 仍是 `cfconsole.config.v1`，**不用升版本**：老数据读进来这两个字段自动是 `""`，而 `""` 的意思就是"不传 `?account=`"，行为与升级前一致；写入时存储里会多出两个空字符串字段，那是格式变化不是行为变化。读写两侧都只认 32 位 hex，脏值存不进去）；`api.ts` 的 `gw()` 自动注入 `account`，`/v1/accounts` 与 `/health` 在豁免名单里；设置页新增「这把令牌能看见的账号」卡片（1 个账号就明说不给切换器，多个才出「选它」按钮）；顶栏加第二个 tag 显示账号名 —— 只有一个账号时它是空的，别为了做功能而塞满界面。
8. **界面又抓到两处说谎**（我自己造了失效状态才看得见的，`09` §E17 同一类问题的第五、六例）：

### 10-10 深夜第五段（**降 CF 出网次数：网关 5 分钟缓存 + 时间窗对齐 + 请求合并；账号侧零变更**）

他这一句是「降低网关对 cf 的请求次数，改成进 app 一次加每隔 5 分钟请求一次，能合并的请求也一起合并了」。做成三层，都用同一把尺子（`CACHE_TTL_MS = 300_000`）对齐。

1. **网关 `CfClient.send()` 层缓存**（`app/gateway/src/cf.ts`）：TTL 5 分钟的内存 Map + in-flight 合并（同一 key 并发只发一次，其余等同一个 promise）。**只缓存读**：`GET`、`/graphql`、`*/analytics/sql`；任何写语义的调用连 key 都不生成，直接出网 —— 这条是硬边界，别哪天把写也缓存了。缓存键是 `FNV(令牌)|method|path|FNV(body)`，**令牌原文不当键**（key 只在内存，绝不进任何响应）。
2. **时间窗按 5 分钟整格对齐**（`catalog.ts` 的 `parseRange`）：这是本轮唯一"不这么做缓存就等于没做"的一环。原先窗口取"此刻"往前推 N 天，每次的 query 串都不一样 ⇒ 缓存键永不相同。实测对比很直白：**没对齐时 warm 轮仍剩 4 次出网，对齐后 0 次**。代价要讲清楚：看板上的数据窗最多旧 5 分钟（界面显示的是真实取数时刻，见第 6 条）。
3. **GraphQL 合并**：看板的「1dGroups 大数字 + adaptive 的 visits/字节 + adaptive 的国家分布」原本是 2–3 条查询，现在在同一个 `viewer.accounts` 层用三个 alias（`g`/`v`/`a`）合一，`overview` 从 **4 次 CF 降到 3 次**（1 条 GraphQL + 2 条 SQL）。代价是三块卡同生共死（一起成功或一起空），缓存之后这个代价摊薄成"5 分钟里最多一起错一次"，可以接受。
4. **有一处合并被实测证伪，所以没做**：`GET /zones/{z}/rulesets` 一次返回 4 条 ruleset，看着正好替掉 WAF 那 3 条 entrypoint 请求；但它返回的 custom/managed 里 **`rules` 是 0 条**，而 entrypoint 实测有 **1 条生效规则**。用它就会把「有规则」显示成「0 条规则」，那是界面说谎不是省请求 —— WAF 仍然老老实实 3 次。
5. **前端也加 5 分钟内存缓存**（`app/console/src/lib/api.ts`）：这一层省的是手机流量和来回 HTTP（从 Worker 详情退回列表、再进另一个 Worker，同一份数据不该再要一遍）。「刷新」按钮走 `forceFreshWindow()`：接下来 20 秒内的请求都带 `?fresh=1` 并绕过两层缓存，**不做"点了刷新其实拿到缓存"**。
6. **可观测与界面诚实**：响应头三件套 `x-gw-cache`(local/hit/mixed/fresh/miss) / `x-gw-fetched-at`（网关真正取数的毫秒时刻）/ `x-gw-cf-calls`（这条响应出网几次），`/health` 加 `cache:{ttlMs,entries,cfCalls,cacheHits,coalesced,hitRate,scope:"isolate"}`。看板那行文案改成「数据取自 \<真实时刻\>（\<从哪一层拿的\>）· 同一时间窗网关 5 分钟才出网一次」，删掉了原来那句已经不符事实的「一次刷新 = 网关 4 次 CF 请求」。
   顺带抓到三个我们自己的谎，都是浏览器实测时才暴露的：
   - `gwMeta` 是普通对象，在 `gw()` 里就地改值不触发 Vue computed 重算 ⇒ 那行「数据取自…」**压根没渲染出来**（`v-if` 永远拿首次求值的空串）。改成 `reactive()`。
   - `fmt.ts` 的 `dt()` 只认 ISO 字符串，把 epoch 毫秒当数字传进去会**原样印出 `1791637506524`**。现在数字按毫秒时间戳处理。
   - "多少秒前"是用请求返回那一刻算死的，盯着页面看四分钟还写「5 秒前」⇒ 改成页面 10 秒时钟重算，`onUnmounted` 清掉。
7. **实测数字**（`tools/probe-request-budget.mjs`，一圈 = 六屏实际会发的 **18 条**网关往返）：
   ```
   ① 强制刷新  网关往返 18 条 · 出网 CF 22 次 · /health 累计差值 22 · {"fresh":18} · 墙钟 13816ms
   ② 再逛一圈  网关往返 18 条 · 出网 CF  0 次 · /health 累计差值  0 · {"hit":18}   · 墙钟   670ms
   ③ 第三圈    网关往返 18 条 · 出网 CF  0 次 · /health 累计差值  0 · {"hit":18}   · 墙钟   713ms
   ```
   两个计量口径（响应头合计 vs `/health` 累计差值）现在**完全对上**。上一轮记的「14 条 / 16 次」和那个没解释清楚的「16 vs 17」，根因是**探针自己多打了一条**：取 zone id 时又 `hit()` 了一次 `/v1/zones`，那次出网进了 `/health` 累计却没进头部合计；同一处写法还暴露上一轮**漏跑了域名屏那 4 条**（拿 zones 的方式不对，循环空转）。本轮改成复用本轮已跑过的 `/v1/zones` 响应，数字因此变大、结论方向不变：**冷一圈 22 次 → 5 分钟内复用 0 次**。计量工具自己不能是噪声源，这条记在这儿。
   浏览器里 `local / hit / fresh` 三态的实际文案都验到了（「本机内存里的数据（1 分钟前取的）· 没发请求」「网关缓存复用…这次一次 CF 都没打」「强制刷新 · 本次出网 3 次 CF（看板 3 条：1 条 GraphQL + 2 条 SQL）」）。
8. **局限要说明白，别当成硬承诺**：内存缓存按 isolate 分格 ⇒ "5 分钟一次"是 CF 出网次数的**下界，不是上界**（冷启动、被调度到新 isolate 就重新取一轮）。没上 KV 是因为要建 namespace（账号变更，得他点头），Cache API 对 POST 无效，所以这两条路都没走。
9. 回归：网关 `tsc` 与前端 `vue-tsc` 干净、`vite build` 过（`index.js` **163.27 kB / gzip 62.68 kB**）、`smoke-gateway` **39 通过 / 0 失败**（这轮冒烟会命中缓存，通过项没变）、`check:routes` 28 条路由全命中、`check:pwa` **8 个引用全绿**（临时起 `vite preview --host 127.0.0.1:4174`，跑完已关）。
10. **账号侧零变更**：只读、没 deploy。线上 `cf.acct.example.com` 的**静态界面和网关都还是旧版** —— 界面第二阶段 + 本轮缓存层全部堆在本地，等他放行重新部署。

用第一种就不用再管权限了：`wrangler deploy` 和 `wrangler secret put` 检查的都是 `Workers Scripts Write`，你 2026-10-10 确认这把令牌有，`05` §1 的错误码证据也是同一答案 —— **4.1 不存在"缺权限所以部署不上去"这种阻塞**，等的只有你点头。

```bash
cd «LOCAL_PATH»
wrangler login   # 或者用现有令牌，跳过
wrangler secret put CF_API_TOKEN      # 交互式粘贴，值来自 «LOCAL_PATH»
wrangler secret put CF_ACCOUNT_ID
wrangler secret put DEVICE_TOKENS     # 逗号分隔，先只放 .device-token 那一个

```

影响面：账号里多一个名为 `cf-console-gateway` 的 Worker（免费额度内）。回滚：`wrangler delete --name cf-console-gateway`。
风险：部署本身不动你现有 7 个 Worker；但部署完默认会有 `cf-console-gateway.<子域>.workers.dev` 这个地址，**在你这个网络访问不到**，所以只做部署没意义，必须配 4.2。

### 4.2 给网关绑一个你自己的域名（二选一）—— **✅ 已于 10-10 深夜按 A 案执行**

- A 案（推荐，改动最小）：Workers 自定义域名
  `PUT /accounts/{a}/workers/domains`，body `{"hostname":"cf.acct.example.com","zone_id":"20017d32…","service":"cf-console-gateway","environment":"production"}`
  这条**会同时建 DNS 记录并签一张 Advanced Certificate**（实测路由可达、到业务校验层 `10082`，但完整链路没发过有效请求 = 风险 B3）。
- B 案：wrangler 路由
  在 `wrangler.toml` 加 `routes = [{ pattern = "cf.acct.example.com/*", zone_name = "acct.example.com" }]` 再 deploy。

需要你先定的：**子域叫什么**（我默认按 `cf.acct.example.com` 写），以及是否接受多一张证书（CA 有速率限制）。

> **权限口径（2026-10-10 晚间我写过一版"必须先把 4.3 做完"的顺序更正，那版是错的，这里撤回）**：
> **并且这条已经在深夜被实测结案了**：真发一次 `PUT` 之后，CF 自己建了那条 AAAA 记录并签了证书，而这把令牌的 DNS 写权限实测是缺的（`403 10000`）—— 建记录走的是平台侧，不查令牌的 DNS 权限。下面保留"当时怎么错的"这段，是为了记住"手抄表不能当排期依据"这条教训。
> 我当时读到的 `05` §3 那条手写表写着「`Workers Scripts Write` + `DNS Write`（两条都要）」，就顺手把它当成了 A 案的前置条件。
> 但 `10-API-全量清单.md` 是从官方 OpenAPI 直接生成的，那条 `PUT /accounts/{account_id}/workers/domains`（Attach Worker Domain）的
> `x-api-token-group` **只有 `Workers Scripts Write` 一条**，没有 DNS。生成的表赢，手抄的表错，已把 `05` §3 那行订正。
>
> 所以 A 案的真实情况是：**鉴权层面现在就能过**（`05` §1 实测 `PUT` 到的是业务校验码 `10082`，不是 `10000`），
> 不以 4.3 为前置。仍然没实测的是**副作用**：CF 收到这次请求后会不会以平台身份顺手建 DNS 记录、签 Advanced Certificate
> （这就是风险 B3），这个跟令牌权限无关，只能发一次真请求才知道，所以要你点头。
>
> 这里有一条要如实标出来的边界：`10082` 那次探测用的是**非法域名**，请求在业务校验层就被打回了，所以"CF 后面真的去建 DNS
> 记录时，会不会再回头查一次令牌的 DNS 写权限"这件事**没被任何一次实测覆盖过**。规格表说这一个 operation 只要
> `Workers Scripts Write`，那是目前最好的依据，但它是文档证据、不是实测证据。
>
> 4.3 的正确定位退回原样：它 gate 的是**App 里的 DNS 编辑与清缓存这两个功能**（当前实测 `403/401 code 10000`，真缺），
> 不是 4.2 的前置。但正因为上面那条没实测，而 4.3 是"你在浏览器里点几下、不动任何资源"的零风险动作 ——
> **建议跟 4.1/4.2 同一次后台操作里顺手勾掉当兜底**，勾了不亏，不勾的最坏结果也只是 4.2 那一次 `PUT` 回来一个可以照着改的错误码。
>
> **4.1 / 4.4 / 4.5 也没有权限阻塞**：你 2026-10-10 确认这把令牌带 Workers 与 Pages 的写权限，
> 与 `05` §1 的错误码证据（脚本写 `10210`/`10001`/`10026`、Pages 假项目 `404 8000007`）一致 —— 都过了鉴权层。
> 所以我之前提议的"故意非法 `PUT` 探一次部署权限"确实可以省掉，那张错误码证据 + 你的确认就是答案。
> 唯一还没测过的是 B 案的 `Workers Routes: Edit`（Zone 级），所以 B 案不自动更省事；A 案仍然是默认选择。

### 4.3 补令牌权限 —— **✅ 权限已到手（10-10 深夜，用 API 建的专用令牌，不需要你登录后台）**

原话是「得你在后台勾」。**这句作废**：那把生产令牌自带 `Account API Tokens Write`，`POST /accounts/{a}/tokens` 实测能建成新令牌（完整过程与证据在上面 §2「深夜第二段」）。做法是**不动生产令牌**、新建一把 14 组的 `cf-console-gateway` 并把网关 secret 换成它，`DNS Write` 与 `Cache Purge` 都在新令牌上实测生效（`400 9000` 与 `200 success:true`）。

**剩下的不是权限，是代码**，这部分我要动手、而且写完也不会对你的 zone 产生任何变更，直到你说"跑一次真的"：

1. `catalog.ts` 加写端点表（`POST/PATCH/DELETE /zones/{z}/dns_records[/{id}]`、`POST /zones/{z}/purge_cache`），沿用同一套"路径片段只能来自白名单"的规则。

## 5. 界面上现在会"空"或"降级"的地方（都是诚实的空，不是 bug）

2026-10-10 起，界面对三种"没有数字"用了三套文案，不再共用 0：**没取到**（请求失败）、**取数中**（还在路上）、**确实没有数据**（接口回来了且为空）。起因是实测抓到假令牌 401 时看板显示"请求数 0"，见 `09` §E17。下面表里凡写"空状态"的都指第三类。晚间做多账号时又冒出**第四类**：**已失效的用户选择** —— 它既不是"没取到"也不是"确实是 0"，而是"你上次选的东西现在不能用，界面正在用别的"，必须有自己的文案（见下面账号那一行与 §2 晚间第 8 条）。

| 位置 | 现象 | 原因 |
|---|---|---|
| Pages 整页 | 空状态文案 | 账号 0 个项目（风险 A1）——列表接口正常返回 0 条，属于"确实没有" |
| 看板 四张指标卡 / 时序 / 状态码 / 来源国家 / 下钻 | 失败 → "—（没取到，不是 0）"，加载 → "—（取数中…）"，下钻未查 → "还没查：…"，查完为空 → "确实没返回条目"；两者都不画 0、不画空图 | `09` §E17，浏览器实测四档（含 `timeout` 与 `network` 两种错误分开的文案） |

### 19.9 数据库屏：左列表搜索（观感层，零新请求）

### 19.10 字体改成"跟随本机"（观感层）
