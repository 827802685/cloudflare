## 3. wrangler 本地开发闭环（实测）

- 安装耗时约 1 分钟，`node_modules` 172 MB / 37 包；要 Node ≥ 22（本机 v24.13.1）。
- 沙箱 `«LOCAL_PATH»`：`wrangler dev` 起在 `127.0.0.1:8787`，Worker 内部 `fetch("https://api.cloudflare.com/client/v4/accounts")` **成功拿到真实账号数据** → 说明"网关代理 CF API"这件事在本地就能全程验证，不用先部署。
- `wrangler dev` 会尝试拉 `cf.json`，失败只 warn，`request.cf` 降级为占位，不影响主流程。
- 三个坑（都踩过）：
  1. `send_metrics` 现在必须是布尔值。写成 `"off"` 或 `{disable=true}` 会让整个 `wrangler.toml` 解析失败：`Expected "send_metrics" to be of type boolean but got {"disable":true}`。
  2. Node 24 下不能用 `child_process.spawn("npx.cmd", ..., {shell:false})` 起 wrangler，会 `EINVAL`；要 `spawn(process.execPath, ["node_modules/wrangler/bin/wrangler.js", ...])`。
  3. 你现有 Worker `rin-server` 的 `wrangler.toml` 是 bun 项目产物，本地 `wrangler dev` 会因 `send_metrics` 写法报错——这条只影响你复用它的配置，不影响新建项目。

## 4. 令牌的两个致命假象

1. **`GET /user/tokens/verify` 返回 401 `code 1000 Invalid API Token`，但同一个令牌 `GET /accounts`、`/zones`、`/workers/scripts`、`/dns_records`、`/kv`、`/d1` 全部 200。**
   原因：这是 **account-scoped token**，用户级接口没有认证主体（`GET /user` 更直接：`403 code 9109 Valid user-level authentication not found`）。
   → **App 的"登录态判断"必须用 `GET /accounts`，不能用 `tokens/verify`。** wrangler 的 `whoami` 也因此不可靠。
2. **权限不足和令牌无效的错误码不一样，必须分开处理**（实测，见 `05` 分册）：
   `6003/6111` = 令牌格式/值坏；`10000/10001` = 认证/参数错误；`1000` = 令牌无效或缺作用域；`1404` = 无配额（服务没开）；`10042` = 服务未在后台启用；`7003` = 路由不存在或对象 ID 非法；`410` = 接口已废弃。
   → App 里"这个功能灰掉"和"请你重填令牌"必须是两条不同 UI 分支，否则会一直误报令牌失效。

## 5. 63 次请求的结果统计

```
合计 63 次请求：成功 41 · 4xx 有明确语义 20 · 异常 2
```

异常 2 项都是 `500` 且响应体为空：`GET /accounts/{a}/analytics_engine/datasets` 和 `GET /accounts/{a}/analytics/engine_usage/sum`。换了参数形状（`limit`/`offset`/`dataplane`/`v2` 路径/`column/definitions`）**五次全是 500**，所以这不是我们的请求写错了，是这条路径在你这个账号上就是不工作（很可能 Analytics Engine 未产生过数据集）。**结论：Workers/AE 用量不能依赖这几个 REST 接口，见 `01` 分册的替代方案。**

单请求耗时：REST 常态 300–900 ms；Analytics SQL 40–90 ms（服务端）+ 一次网络往返；GraphQL 280–750 ms。

（后续用官方 OpenAPI 规格复核时确认：这两个 500 的路径 `analytics_engine/datasets` 与 `analytics/engine_usage/sum` **在规格里已经不存在**（前者只剩 `/analytics_engine/sql`，后者整族下架），所以不是我们请求写错，也不是权限问题 —— 见 `10-API-全量清单.md` §2 与 §6。）

## 7. 一个会骗人的 API 行为（重要）

**Workers 相关路由会忽略无法识别的路径后缀，回落成父资源。** 实测三例：

- `GET .../workers/scripts/rin-server/versions/{v}/content` → 200，返回的是**版本对象 JSON**（和 `versions/{v}` 一模一样，4029 字节），不是代码。
- `GET .../workers/scripts/rin-server/analytics` → 200，返回的是**整包 multipart 代码**（2558574 字节）。
- `GET .../workers/scripts/rin-server/tail-sessions` → 同上，也是整包代码。

但 `versions/{bogus-id}/content` → 404 `100146`，说明**版本 ID 是被解析的，只是尾巴被丢掉**。

→ 写客户端时**不能只判断 HTTP 200 就认为端点存在**，必须同时校验 `content-type` 和响应结构；否则会出现"版本代码下载成功，界面显示一坨 JSON"这种诡异 bug。目前**没有公开的"下载指定历史版本源码"接口**，只能下载当前部署的整包。
