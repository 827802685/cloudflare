## 0. 先说三条会影响「能不能抄」的硬结论

1. **Workers 的版本回滚 / 灰度百分比在这款 App 的 UI 层不存在。**
   - 回滚接口在 API 层有（`CloudFlareApi.kt:286-297`，`POST .../versions/{id}/deploy`），ViewModel 也封装了（`WorkerViewModel.kt:863-883`，成功时发「回滚成功」文案），但对全部 `.kt` Grep `deployWorkerVersion` 只命中这两处，**没有任何界面文件调用它** → 用户点不到。
   - 版本历史列表里**没有回滚按钮**：`WorkerHistoryAdapter.kt:27-49` 每行只有「编号 + 短 ID + 时间 + 来源 + 运行中徽章 + 删除」，且运行中时删除也被隐藏（L40）。
   - 灰度百分比在 API 层有（`CloudFlareApi.kt:329-341` 创建 deployment 策略），但 UI 只有上传完成后一个「切换生产流量」开关，写死 100%（`fragment_worker.xml:219`；`cfa-strings.xml:2553-2554`「将最新版本 100% 切到生产环境（deployment percentage 策略）」；`WorkerViewModel.kt:176-196` `percentage = 100`）。
   - **结论：这块我们只能抄它的「展示骨架」（版本卡片字段、徽章、排版），切换交互必须我们自己设计。** 相关处一律写「未取到」，见 §2。

2. **Pages 的部署切换是完整的、可直接照抄的：** 每行有「回滚」「重试」按钮 + 明确确认文案（`PagesDeploymentsAdapter.kt:65-73`、`PagesFragment.kt:3248-3297`）。四块里交互最完整的参考就是 Pages。

3. **「域名流量」和「DNS/站点管理」在竞品里是两套独立屏，不要混为一谈；缓存清理也不在 DNS 屏。**
   - 流量 = `DashboardCardView`（`fragment_zone_analytics.xml` + `card_dashboard.xml` + `DashboardCardView.kt`）。
   - 站点列表 / 工具入口 = `DomainListFragment.kt` / `DomainDetailFragment.kt`（用户清单里写的 `fragment_domain_list.xml`、`fragment_domain_detail.xml` 属于这里，不是「Workers 自定义域名」）。
   - 真正的「Workers 自定义域名」屏是 `RouteFragment.kt`（首页 `customDomainCard` → `action_home_to_route`，见 `HomeFragment.kt:308` 与 `nav_graph.xml`；`item_custom_domain.xml` 的实际消费者是 `RouteFragment.kt:688`）。
   - 清理缓存入口在 `ZoneSettingsFragment.kt:129-224`（固定四行工具列表），不在 `DnsFragment.kt`。

## 1. 全局骨架范式（所有列表屏共用的一层壳）

竞品的四个目标屏（Workers、DNS、Pages、路由/自定义域名）用的是**同一个屏级模板**，这是我们最值得整体照搬的东西。

### 1.1 屏级结构（自上而下）

**A. 「管理 / 新建」型屏（Workers、Pages）**

| 序号 | 区块 | 规格 | 出处 |
|---|---|---|---|
| 1 | 可折叠「部署」卡片 | 顶部一行「卡片头」（标题 + 折叠箭头），点击整行折叠/展开卡片体；默认展开 | `fragment_worker.xml:33-59`（`deployCardHeader`）/ `61-248`（`deployCardContent`） |
| 2 | 卡片体·标识区 | 名称输入框、兼容日期、兼容标志、文件路径 +「选择文件」+「上传/部署」按钮、上传进度条 | `fragment_worker.xml:78 / 94 / 111 / 129 / 138 / 146 / 241`；Pages 对应 `fragment_pages.xml:20-220`（多一个「分支」默认 `main`，按钮为「创建项目」+「部署」双按钮） |
| 3 | 卡片体·开关区 | 一排 `MaterialSwitch`，每个开关**单独一行**：行左文案 + 行右开关；一屏内 3~4 个 | `fragment_worker.xml:154 / 175 / 197 / 219` |
| 4 | 列表工具条 | 一行：左侧标题 + 右侧 3 个文字按钮，权重 2:3:3:2 | `fragment_worker.xml:288 管理版本 / 297 管理脚本 / 306 刷新`；`fragment_pages.xml:240-285 管理部署 / 管理项目 / 刷新` |
| 5 | 批量操作条 | 进入选择模式才出现的横条：选中状态文案 + 全选 + 批量删除 | `fragment_worker.xml:316-353`（`selectionStatusText` / `selectAllBtn` / `batchDeleteBtn`） |
| 6 | 列表 | `RecyclerView`，全高 | `fragment_worker.xml:355` |
| 7 | 空态 | 列表下方居中文本 | `fragment_worker.xml:362`；DNS 为空态两行「暂无 DNS 记录 / 点击 + 添加」 |
| 8 | 全屏进度 | 独立 progressBar 覆盖层 | `fragment_dns.xml`；`fragment_pages.xml` |

**B. 「纯列表 + 新建」型屏（DNS）**

列表 → 底部右下角 `FloatingActionButton`（加号）→ 全屏 progressBar → 空态文本。没有折叠卡片、没有工具条。出处：`fragment_dns.xml`、`DnsFragment.kt`（全文已读）。

**C. 「左右分栏」型屏（路由 / 自定义域名）**

50/50 两个面板，**每面板各自独立**拥有：面板头 + `RecyclerView` + progressBar + 空态 + FAB。出处：`fragment_route.xml`（已下载并读）。

### 1.2 列表行通用范式（重要）

竞品的「一行」不是单值行，而是 **「两行文本 + 一个可展开的动作宫格」**：

- 第 1 行：**粗体主标识**（左）+ 一个**文字型图标按钮**（右，如「日志」）+ 展开/收起按钮。`item_worker_script.xml:30 / 39 / 74`
- 第 2 行：**灰色元信息串**，用「•」分隔。`item_worker_script.xml:56`，实测形如 `12.5 KB • 2025-12-13`
- 第 3 块：**功能按钮宫格** `GridLayout`，`columnCount=4`，默认只显示前 8 个，其余靠「展开」。`item_worker_script.xml:67`，`WorkerFragment.kt:3966-3978`
- 宫格按钮样式：**上图下文**，图标 20dp，文字 11sp、`colorPrimary`、最多两行。`WorkerFragment.kt:3911-3964`
- 行整行点击 = 进详情（不是选中）；仅在选择模式下整行点击 = 切换选中，选中行 `alpha 0.8` + 灰底。`WorkerFragment.kt:4028-4037`

### 1.3 反馈层统一约定

| 场景 | 形态 | 出处 |
|---|---|---|
| 一般成功 / 失败 | `Snackbar`（底部浮出） | `DnsFragment.kt:109-112`；ViewModel 发 `UiMessage` → Fragment 统一转 Snackbar |
| 关键操作确认 | `MaterialAlertDialogBuilder`，标题 + 正文 + 取消 + 正向按钮 | `WorkerFragment.kt:2112-2137 / 2569-2690 / 3345-3365`；`PagesFragment.kt:3248-3297` |
| 异步拉详情 | 先弹一个「加载中」对话框，拿到数据后**原地替换内容** | `WorkerFragment.kt:2045-2110`；`PagesFragment.kt:2436-2462` |
| 行内溢出菜单 | 三点 `PopupMenu`，共用 `menu_account.xml`（设为默认 / 编辑 / 删除），按场景隐藏其中若干项 | `DnsFragment.kt:429-448`；`RouteFragment.kt:717-733` |
| 校验失败 | 输入框下方红字 或 `Snackbar`，视屏而定（见各屏） | §2~§5 |
| 不可逆操作 | 确认文案里显式写「此操作不可恢复 / 不可撤销」 | `PagesFragment.kt:3248-3260`；`ZoneSettingsFragment.kt:129-136` |

## 2. 屏级规格 · ② Workers 版本查看与切换

见 §1.1-A（Workers 即该模板的原型）。列表 = 脚本列表；**版本不是列表屏，是弹窗**。

### 2.2 列表行字段清单

脚本行（`item_worker_script.xml:30 / 39 / 56`）：
1. 脚本名（粗体，单行）
2. 「日志」文字图标按钮
3. 元信息串：`大小 • 最后修改日期`，日期统一换算 `Asia/Shanghai`（`WorkerFragment.kt:4050-4064`）
4. 展开/收起按钮
5. 16 个动作按钮宫格（默认显示 8 个）

**16 个动作按固定顺序**（`WorkerFragment.kt:3838-3854`）：
KV 命名空间 / R2 存储桶 / D1 数据库 / 服务绑定 / 变量 / 机密 / 设置 / 删除 / 触发器 / 部署记录 / 编辑脚本 / 添加域名 / 查看域名 / 添加路由 / 查看路由 / 功能开关。

### 2.3 版本历史弹窗（「管理版本」入口 → `WorkerFragment.kt:2779-2890`；单脚本「部署记录」→ `2045-2110`）

- 打开时**先显示加载对话框**（`2052`），数据回来后填列表。
- 列表为空 → `Toast`「暂无版本历史」（`2101`）；请求失败 → `Toast` 错误文本（`2105`）。
- 版本行字段（`WorkerHistoryAdapter.kt:27-49`）：
  1. `#倒序编号 - 短ID（8 位）`（L31）
  2. 创建时间（L32）
  3. `来源: %s`（L35）
  4. 「运行中」徽章（L38）
  5. 删除按钮（**运行中时隐藏**，L40）
  6. 整行点击 → 版本详情弹窗（L46）
- **「运行中」的判定方式**：`versions.firstOrNull()?.id`（`WorkerFragment.kt:2067`）——即拿列表第一个当当前版本，**这是猜的，不是读 canonical 字段**。我们的 PWA 应改用 API 返回的 `canonical_version` / 最新 deployment，不要照抄这点。
- 删除版本确认：`WorkerFragment.kt:2112-2137`（对话框，含版本标识 + 不可恢复语气）。

### 2.4 版本详情弹窗（`dialog_worker_version_detail.xml`，20,057 B；逻辑 `WorkerFragment.kt:2348-2508`）

字段按固定顺序成对呈现（键名 + 值，空值填「-」，`2372-2393`）：
- 基本信息：版本号 / 版本 ID / 创建时间 / 来源 / URL / 作者 / 作者 ID / 预览 / 部署消息（`workers:message`）/ 触发方式（`workers:triggered_by`）—— `2395-2408`
- 部署区块：部署 ID / 部署时间 / 来源 / **策略** / **流量占比 %** / 作者 —— `2426-2444`
- 「运行中」徽章 —— `2446-2464`
- 「访问」按钮：**仅运行中版本才出现** —— `2466`
- 「删除」按钮 + 二次确认 —— `2475-2496`

> 「策略 + 流量占比 %」两个字段（`deploymentStrategyText` / `deploymentPercentageText`）是竞品**展示了灰度状态但不提供灰度操作**的证据：它能看见「这次部署是按百分比、占比多少」，却没有发起百分比部署的入口。

### 2.6 确认与错误提示形态（Workers）

- 删除脚本 / 批量删除 / 删除版本 / 解除域名绑定：一律 `MaterialAlertDialog`，正文点明对象标识与不可恢复语气（`WorkerFragment.kt:2112-2137 / 2569-2690 / 2475-2496 / 3345-3365`）。
- 添加自定义域失败：**AlertDialog**（不是 Snackbar）——竞品里少见的「错误升级」处理（`3030-3034`）。
- 变量/机密/运行时/触发器保存：**Toast 或 Snackbar**，成功失败同渠道（`1872-1878` 等）。
- ⚠️ 反面样本：机密「应用」后是 `delay(500)` 然后**无条件**弹成功 Toast（`WorkerFragment.kt:1872-1878`），根本没等接口结果 —— 这种假成功不能抄。

## 3. 屏级规格 · ③ Pages 部署查看与切换

- 入口带**加载对话框**：`showDeploymentsDialogWithLoading`（`PagesFragment.kt:2436-2462`）→ `showDeploymentsDialog`（`2464-2507`）→ 行点击 → `showDeploymentDetailDialog`（`2509-2771`）。

- 部署行字段（`PagesDeploymentsAdapter.kt:41-83`）：
  1. `#倒序编号 - 短ID（状态）`（L41）
  2. **触发来源本地化**：api / dash / wrangler / github / gitlab / 其他（L44-53）
  3. 「函数」徽章（L56-60）
  4. 「运行中」徽章（L62-63）
  5. **「回滚」按钮：仅当 非运行中 且 状态 == success**（L65-69）
  6. **「重试」按钮：仅源码构建（`source != null`）**（L72-73）

  - **环境变量列表**：`secret_text` 类型显示为 `••••••••` 并打「加密」标签（`2672-2719`）

## 7. 建议照搬的 5 条

1. **「折叠部署卡 + 工具条三按钮 + 批量条 + 列表 + 空态 + 全屏进度」这套屏级骨架**（`fragment_worker.xml:33-362`、`fragment_pages.xml:20-285`）。
   理由：我们四块里有两块（Workers、Pages）天然符合这个形状；把「日常只读操作」放进列表、把「一次性写操作」收进可折叠卡片，移动端一屏就能同时具备概览与入口，不需要页面跳转。这是差距最大、收益最直接的一条。

2. **列表行的「主标识 + 元信息串 + 4 列动作宫格 + 默认 8 项 / 展开」范式**（`item_worker_script.xml:30-74`、`WorkerFragment.kt:3838-3978`）。
   理由：移动端放不下长按钮条，宫格 + 上图下文（20dp 图标 + 11sp 双行标签）在拇指区里可点性与扫读性都好；「默认 8 个 + 展开」避免了把 16 个动作硬塞一屏。直接决定我们的行高与栅格尺寸就能收敛大量设计时间。

3. **「异步详情弹窗 = 先弹加载态、数据回来后原地替换」+「三态容器（loading / error / content）」**（`WorkerFragment.kt:2045-2110`、`PagesFragment.kt:2436-2462`、`DashboardCardView.kt:498-520`）。
   理由：版本 / 部署详情都要先拉一次接口。竞品这套避免了弹窗空白或页面抖动，也让错误态有确定归属位置（不是 Toast 一闪而过）。是可直接落地的组件契约。

4. **状态徽章 + 条件动作 + 「不支持要说原因」的组合规则**：运行中徽章、回滚仅在 `!running && status==success` 出现、重试仅源码构建、「官方不支持编辑」用 Snackbar 点名（`PagesDeploymentsAdapter.kt:62-73`、`RouteFragment.kt:180-185`）。
   理由：这三条把「API 的可用性」直接映射成「界面上按钮的存在与否 + 一句原因」，用户不会点出一个必失败的请求。我们做灰度/回滚时最需要这种可推导的动作显隐规则。

5. **确认文案「点名对象 + 说明后果 + 按钮文字用动词」的三件套**（`PagesFragment.kt:3248-3297` 三类确认各不同话术；`ZoneSettingsFragment.kt:129-136`「此操作不可撤销」；`RouteFragment.kt` 删除路由带引号对象名）。
   理由：成本极低、误操作率显著下降，尤其我们做的是有真实破坏性的切流量/删版本操作。竞品这三处文案结构可以直接作为我们的文案模板。

## 8. 不建议照搬的 3 条

1. **不要照抄它的「运行中/当前版本」判定。** 竞品版本历史用 `versions.firstOrNull()?.id` 猜当前版本（`WorkerFragment.kt:2067`），Pages 用 `canonicalDeployment?.id ?: previewDeployment?.id` 回退（`PagesFragment.kt:2451-2457`）。
   理由：一旦我们要做**灰度百分比**（两块 deployment 并存）或列表非按时间倒序，这个判定就会把错误的版本标成「运行中」，进而把回滚/删除按钮放在错误行上。我们必须以 `canonical_version` + 最新 deployment 的百分比为唯一真相。

2. **不要照抄它的反馈渠道与「假成功」。** 具体三例：机密「应用配置」后 `delay(500)` 无条件弹成功 Toast（`WorkerFragment.kt:1872-1878`）；变量/运行时/触发器保存成功失败都只走 Toast；DNS 删除确认不带记录名（`DnsFragment.kt:261-272`）；DNS TTL 非数字被静默改成 1（L212）。
   理由：切流量和删除版本是不可逆的写操作，「没等结果就报成功」会让用户以为线上已生效。我们要统一成「请求完成 → 按真实结果反馈 → 失败必须留下可读错误（参考它做得好的 Pages 域名行错误文本 `PagesFragment.kt:3222-3231`）」，而不是全面模仿 Toast。

3. **不要照抄它的 N+1 拉取、无入口的死菜单与「装饰性粒度」。**
   - `WorkerFragment.kt:3674-3691`：查看路由先拉所有 Zone、再逐 Zone `listRoutes`；`WorkerFragment.kt:3299-3372` 的域名弹窗也走同类多轮请求。移动端一多 Zone 就明显变慢，我们应在自己的聚合层/后端做批量。
   - `PagesFragment.kt:478-510` 的「项目管理」十项弹窗 **Grep 无任何调用者**，而卡片按钮把环境**写死成 `production`**（L221-270）；`showProjectManagementDialog` 是竞品留给我们最好的反面教材：**别在 UI 上摆出实现不了或多重的入口**。
   - `PagesFragment.kt:443` 注释自己承认「Pages API 会同时更新两个环境，环境 chip 只是装饰」。理由：界面给出「生产 / 预览」切换却底层不分，比不给切换更危险——用户会以为只改了预览。我们要么真按环境作用域请求，要么在 UI 上明说「该操作影响两个环境」。
