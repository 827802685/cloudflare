# 05 · 令牌权限边界与要新建的令牌

当前令牌：`F:\Documents\GitHub\Rin\.env.local` 里的 `CLOUDFLARE_API_TOKEN`（`cfat_` 前缀，**不打印内容**）。`GET /accounts/{a}/tokens` 能看到它的元信息：`id=61d0d0fb…`、`name="dark-lake-83f6"`、`status=active`、`issued_on=2026-07-31`。它就是 `versions[].metadata.author_id` 里那个 ID —— 也就是说你的 Worker 版本历史里"谁传的"记的是令牌 ID，不是用户 ID。

**权限明细读不到**：`GET /user/tokens/{id}` 属于用户级接口，被 `403 code 9109` 挡住。所以下面这份能力表是我用 63 次真实调用逐条试出来的，不是查配置文件得来的。

## 1.5 10-10 深夜：4.3 不必登录后台就能做完（推翻本节原先的说法）

本节和 `11` §4.3、`12` §2 原来都写着"这两项要**你本人在网页后台勾**，我碰不到后台"。**那句是错的**，错在我从没试过用令牌管令牌的接口。当晚实测三组：

| 探测 | 结果 | 结论 |
|---|---|---|
| `GET /accounts/{a}/tokens` | **200**，列出账号里 2 把令牌及各自权限组 | 令牌能读账号作用域的令牌清单 |
| `GET /user/tokens` | `403 code 9109` | 用户级那一半不行（account-scoped 令牌的正常表现，`09` §E 里已把 9109 归为"不是坏令牌"） |
| `PUT /accounts/{a}/tokens/{不存在的 32hex}` | `404 code 1003 "Token not found"` | 动词支持 + 鉴权已过，停在"资源不存在" |
| `POST /accounts/{a}/tokens`（故意空 body） | `400 "name must be present / policies must be present"` | 建令牌也停在参数校验，不是 `10000` |

再回看 `GET /accounts/{a}/tokens` 的返回，生产令牌那 326 个权限组里**本来就有 `Account API Tokens Write`** —— 也就是说"补权限"这件事被这把令牌自己就能干。

于是选了比"改生产令牌"更稳的做法：**新建一把只含四块功能所需权限的令牌**，14 个权限组逐个从 `F:/work/openapi.json` 的 `x-api-token-group` 反查出来（脚本 `F:/work/tmp/perm-plan.mjs`，临时件已删；口径同 `10` 的生成表，不是手抄）。换 secret 后本地与公网的 39 条冒烟都是全绿，逐条记录在 `11` §2「10-10 深夜第二段」。

> 两处留存的本地件（都不在仓库里）：`GET /accounts/{a}/tokens/permission_groups` 那 407 条权限组目录缓存在 `F:/work/cf-permission-groups.json`（4.4 若还要反查权限组直接拿它，不必再打 API）；**换下去的旧令牌值备份在 `F:/work/tmp/dev.vars.bak`**，那是"secret put 回旧值"这条回滚路径的唯一本地依据，别当垃圾删。

两条副产品：

1. 建令牌时 `resources` 的**写法只认嵌套**。flat 的 `{"com.cloudflare.api.account.zone.*":"*"}` 被拒 `400 code 1001 "Must specify a zone for account owned tokens, or nest zone under specific account resource"`；要写成 `{"com.cloudflare.api.account.<ACC>":{"com.cloudflare.api.account.zone.*":"*"}}`（`09` §E21）。
2. 新令牌的 `Cache Purge` 是**真的生效了**：我那条按惯例故意填成 `files:[123]` 的探测没有被拒，而是回了 `200 success:true` —— 这是一次真实执行的 purge 调用（目标字符串不匹配任何缓存 URL，等效空操作，但它不是"被闸门拦住"）。写侧探测第一次出现"探测本身打出去"的情况，`09` §B5 已按这个口径改写。

> 2026-10-10 令牌持有人补充确认：这把令牌**本来就带 Workers 与 Pages 的写权限**。这与上表一致 —— "Workers 脚本写""自定义域名绑定""Pages 写"三行返回的都是业务码而不是 `10000`，说明它们都过了鉴权层。
> 所以「4.1 部署网关 / 4.4 写链路 / 4.5 建 Pages 项目」这三件事**没有权限阻塞**，等的只是逐条放行。
> 需要说明的是证据强度不同：这三行的**实测**只到"鉴权层过了、请求在业务校验或资源不存在处停下"，"写入真的成功落库"这件事在任何一条写路径上都还没发生过（那要等 4.4 在测试 Worker 上闭环）。
> 换句话说：持有人确认的是**权限**，未验证的是**写链路的请求体形状与副作用**（`09` §B1/B2/A2）。

## 2. 错误码语义对照（App 里要按这个分支）

| code | 含义 | UI 该怎么表现 |
|---|---|---|
| `6003` + `error_chain.6111` | 请求头里 Authorziation 格式坏（不是 `Bearer ` 前缀问题就是令牌值被截断） | "令牌没填对"，引导重填 |
| `1000` / `10001` Authentication error | **令牌对该资源没有对应权限**，或作用域不含这个 zone | "这把令牌缺 XX 权限"，给出要补的权限名（见 §3） |
| `9109` | account-scoped 令牌调用了用户级接口 | 静默处理，这类接口不要放进 App |
| `10000` 伴随 403/401 | 同上（DNS / purge 就是这个） | 灰掉该功能 + 提示补权限 |
| `10007` This Worker does not exist | 脚本名写错（记住脚本名在 `id` 字段不在 `name`） | 内部错误，别当成权限问题 |
| `100146` | 版本 ID 找不到 | 正常业务提示 |
| `10405` Method not allowed for this authentication scheme | **动词不对**（例如 `GET /workers/tails` 只允许 POST 创建），不是权限 | 别报"无权限" |
| `7003` / `7000` Could not route / No route for that URI | 路径本身不存在，或该服务未在后台开通 | "此服务未开通" |
| `10042` | R2 未启用 | "请先在控制台启用 R2" |
| `1404` No quota allocated | 套餐无配额（SSL for SaaS 等） | 直接砍功能 |
| `410` + deprecated | 接口已废弃 | 走新接口，别提示用户 |
| `8000007` | Pages 项目名不存在 | 正常业务提示 |

## 3. 建议新建的令牌（要做 DNS 编辑 / 清缓存时才需要）

在 **dash.cloudflare.com → My Profile → API Tokens → Create Token**，用 **Custom token**，不要点 Global API Key。

按功能块需要的权限。**官方 OpenAPI 规格里每条 operation 都带 `x-api-token-group`，那是权限的权威名字**（下表中"规格名"列，取自 `docs/evidence/openapi-operations.json`）；后台界面里显示的是 `<Resource>: <Name>: <Level>` 三段式，可能和规格名不完全一样 —— 按关键字搜，以搜到的为准：

| 目标功能 | 规格里的 `x-api-token-group` | Resource | 界面权限项 | 级别 |
|---|---|---|---|---|
| DNS 增删改 | `DNS Write` | Zone | `DNS` | Edit |
| 清缓存 | `Cache Purge` | Zone | `Cache Purge` | Purge |
| 站点设置改动（`PATCH /zones/{z}/settings/{id}`） | `Zone Settings Write` | Zone | `Zone Settings` | Edit |
| 站点本身增删改（本方案不做） | `Zone Write` | Zone | `Zone` | Edit |
| Workers route 增删改 | `Workers Routes Write` | Zone | `Workers Routes` | Edit |
| 流量分析（Analytics SQL / AE SQL） | `Account Analytics Read` | Account | `Account Analytics Read` | Read |
| 流量分析（老 zone dashboard / Argo / DNS Analytics） | `Analytics Read` | Zone | `Zone Analytics` | Read |
| Workers 版本上传/切换、密钥、cron | `Workers Scripts Write` | Account | `Workers Scripts` | Edit（已具备） |
| Tail 日志（`POST /accounts/{a}/workers/scripts/{s}/tails`） | `Workers Tail Read` **或** `Workers Scripts Write` | Account | `Workers Tail` | **实测确认不用补权限**：`POST …/scripts/__nope__/tails` 返回 `404 10007 This Worker does not exist` 而不是 `10000`，说明 CF 先查权限再查资源，我们这关已经过了。真正没验的只有 wss 那条 URL 能不能连（风险 C3） |
| 新版实时日志（`/workers/observability/telemetry/live-tail`、`…/query`） | `Workers Observability Write` | Account | `Workers Observability` | Edit（新面，见 `01` §2.7） |
| D1 查询与写 | `D1 Read` / `D1 Write`（`POST …/query`、`…/raw` 两个都要；`export`/`import`/`time_travel/restore` 规格里**未标**权限） | Account | `D1` | Read / Edit |
| KV 读写 | `Workers KV Storage Read` / `Workers KV Storage Write`（写值 `PUT …/values/{key_name}` 只要 Write） | Account | `Workers KV Storage` | Read / Edit（现只有读） |
| Pages 建项目/部署/回滚 | `Pages Write`（读为 `Pages Read`） | Account | `Cloudflare Pages` | Read / Edit（写路由已可达；2026-10-10 令牌持有人确认这把就有 Pages 写权限） |
| 自定义域名绑定（`PUT /accounts/{a}/workers/domains`） | **只有 `Workers Scripts Write`**（规格里这一个 operation 就这一条，没有 DNS） | Account | `Workers Scripts` | Edit（已具备）。**订正说明**：这一行以前手抄成"`Workers Scripts Write` + `DNS Write`，两条都要"，`11` §4.2 还据此把 4.3 排成了前置 —— 那是错的，已按 `10` 的生成表（line 224，Attach Worker Domain）撤回。**没实测的残留**：CF 真的去建那条 DNS 记录、签那张证书时，会不会以平台身份做（不需要令牌 DNS 权限），还是回头再查一次令牌 —— 我们从没发过有效请求（风险 B3），所以这条只有文档证据、没有实测证据 |
| Account 成员/设置（本方案不做） | — | — | 不给 | — |

> 完整反查表（四块功能里每个写操作对应哪条权限、各覆盖多少个端点）在 `10-API-全量清单.md` §4，那张表是脚本从规格生成的，比这张更全。

**Zone 作用域请选 "Specific zones" → 只勾 `acct.example.com`**，不要选 All zones；Account 同理选具体账号。理由：令牌会被写进手机 App 的网关 secret，泄露面越小越好；而且你的账号只有一个 zone，选全部没有任何收益。

### 建议拆成两把令牌

1. **只读展示令牌**（`rin-readonly`）：Zone Analytics Read + 各资源 Read。App 的看板、列表页只用它。可以随意同步到多台设备。
2. **操作令牌**（`rin-write`）：加上 DNS Edit / Cache Purge Purge / Workers Scripts Edit / Pages Edit。只在你要真的改东西时，在 App 的"设置 → 高危操作令牌"里单独填一次。

这样"我只是想看眼流量"和"我要把域名重绑到另一个 Worker"是两个风险等级，网关侧也能对第二把令牌加二次确认。

## 4. 网关侧的令牌存放（已定，写在这里免得实现时走偏）

- 真令牌**只存在 Worker secret**：`wrangler secret put CF_API_TOKEN`，绝不写进 `wrangler.toml`、绝不进仓库、绝不回传客户端。
- 手机侧只持有一个**设备令牌**（首次启动随机生成，服务端 KV/D1 白名单校验），不是 CF 令牌本身。
- 现在这把 `CLOUDFLARE_API_TOKEN` 在 `Rin\.env.local` 和 `F:\work\cf-probe\app\.dev.vars` 里各有一份明文副本 —— 后者是我这次调研建的临时沙箱，收尾时会删掉（`F:\work` 下的东西不进仓库）。如果以后 App 上线用了更强的令牌，记得 Rin 那边部署脚本也要同步。
